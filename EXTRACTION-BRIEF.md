\# /goal: Извлечение готового универсального интернет-магазина из b2bShop\
\
\## Контекст\
\
Исходный репозиторий: [https\://github.com/hayxe1/b2bShop]\(https\://github.com/hayxe1/b2bShop) \
&#x20;\
Проект представляет собой полноценный интернет-магазин семян «Счастливый Огород», имеющий готовую витрину, каталог, корзину, оформление заказов, платежи, административную панель, складскую логику и другие функциональные возможности. \
&#x20;\
\*\*Задача: создать отдельный, независимый от исходного проекта шаблон полноценного интернет-магазина для дальнейшей продажи магазинам семян и садовых товаров.\*\* \
&#x20;\
Это должен быть не прототип и не декоративная демонстрация, а реальный работающий продукт, готовый к коммерческому внедрению после настройки данных конкретного продавца. \
&#x20;\
\## 1. Главный принцип \
&#x20;\
Не разрабатывать новый магазин с нуля. \
&#x20;\
Не переписывать существующую архитектуру без необходимости. \
&#x20;\
Не упрощать функциональность ради демонстрационной версии. \
&#x20;\
Максимально сохранить текущий b2bShop, поскольку основная разработка уже выполнена. \
&#x20;\
Нужно просто получить независимую, очищенную от конкретного бренда копию проекта, пригодную для многократной адаптации под других клиентов. \
&#x20;\
Все дополнительные доработки и новые требования будущих клиентов будут выполняться отдельно, после получения предоплаты. \
&#x20;\
\## 2. Работа с исходным репозиторием \
&#x20;\
\- Не изменять оригинальный b2bShop. \
\- Создать отдельный проект \`seedshop-template\`. \
\- Сохранить существующий технологический стек. \
\- Не подключаться к оригинальной production БД. \
\- Не переносить реальные данные, заказы, клиентов, остатки и платёжные реквизиты. \
\- Не переносить историю существующих миграций. \
\- Сохранить актуальную Prisma schema и существующие модели. \
\- Предусмотреть и проверить инициализацию новой пустой БД без переноса данных. \
\- Не запускать оригинальный \`prisma/seed.mjs\`, поскольку он содержит операции удаления данных. \
\- Не копировать production-секреты и \`.env\` с реальными ключами. \
&#x20;\
\## 3. Сохранение функциональности \
&#x20;\
\*\*Сохранить весь существующий функционал магазина, включая:\*\* \
&#x20;\
\- Главную страницу и навигацию. \
\- Каталог и категории. \
\- Поиск, сортировку и фильтрацию. \
\- Карточки товаров. \
\- Галереи изображений. \
\- Корзину. \
\- Полноценное оформление заказов. \
\- Систему платежей YooKassa. \
\- Управление заказами. \
\- Административную панель. \
\- Управление товарами. \
\- Существующую складскую логику и остатки. \
\- Систему резервирования. \
\- Существующую оптовую логику. \
\- Наборы товаров. \
\- Подбор семян. \
\- Календарь посева. \
\- Уведомления. \
\- SEO. \
\- Существующие механизмы безопасности. \
&#x20;\
Оптовая логика в исходном проекте уже реализована определённым образом. Не нужно её переделывать, расширять или универсализировать. \
&#x20;\
Аналогично не требуется менять текущую бизнес-логику других модулей без технической необходимости. \
&#x20;\
\## 4. Очистка от исходного бренда \
&#x20;\
Удалить из нового проекта информацию, относящуюся непосредственно к «Счастливому огороду»: \
&#x20;\
\- Название и логотип. \
\- Контактные данные. \
\- Реквизиты конкретного продавца. \
\- Ссылки на маркетплейсы и социальные сети. \
\- Изображения и рекламные тексты, специфичные для исходного бренда. \
\- Упоминания продавца в SEO и JSON-LD. \
\- Брендовые метаданные и иконки. \
&#x20;\
Заменить эту информацию нейтральными значениями или понятными заглушками. \
&#x20;\
Не требуется создавать специальную систему управления брендами или конфигурационный движок. \
&#x20;\
В дальнейшем адаптация будет выполняться непосредственно через Codex. \
&#x20;\
При очистке обязательно проверить отсутствие исходных реквизитов и контактов в публичных страницах, метаданных и уведомлениях. \
&#x20;\
Юридические документы сохранить как структурную основу страниц, но не использовать данные и юридические формулировки оригинального продавца в качестве готовых документов нового клиента. \
&#x20;\
\## 5. Каталог и база данных \
&#x20;\
Не переносить существующий каталог из production БД. \
&#x20;\
Создать независимую пустую базу данных, сохранив структуру необходимых сущностей. \
&#x20;\
Допускается добавить несколько демонстрационных товаров для проверки и презентации: \
&#x20;\
\- Семена томатов. \
\- Семена огурцов. \
\- Семена перцев. \
\- Семена цветов. \
\- Удобрения. \
\- Грунты. \
&#x20;\
Достаточно небольшого набора. \
&#x20;\
Примеры должны быть явно демонстрационными, с условными ценами и разрешёнными изображениями. \
&#x20;\
Создать безопасный способ первоначального заполнения только новой базы, без удаления существующих данных и без зависимости от оригинального seed-скрипта. \
&#x20;\
Не разрабатывать новую систему каталога, складского учёта или импорта товаров. \
&#x20;\
\## 6. Сохранение оформления \
&#x20;\
Максимально сохранить существующий дизайн: \
&#x20;\
\- Структуру страниц. \
\- Стили. \
\- Компоненты. \
\- Анимации. \
\- Адаптивность. \
\- Типографику. \
\- Сетку каталога. \
\- Расположение функциональных элементов. \
&#x20;\
Не проводить редизайн. \
&#x20;\
Не создавать цветовые пресеты, системы динамических тем, визуальные редакторы или дополнительные инструменты ребрендинга. \
&#x20;\
Все изменения внешнего вида в дальнейшем будут выполняться по индивидуальному запросу для конкретного клиента. \
&#x20;\
\## 7. Работающие коммерческие процессы \
&#x20;\
Магазин должен сохранить полноценную возможность: \
&#x20;\
\- Просматривать товары и их наличие. \
\- Добавлять товары в корзину. \
\- Оформлять заказ. \
\- Передавать заказ на сервер. \
\- Обрабатывать и сохранять заказы в БД. \
\- Работать с YooKassa после настройки действительных реквизитов продавца. \
\- Управлять заказами через админку. \
\- Управлять товарами и складскими остатками. \
&#x20;\
Не заменять полноценное оформление заказа демонстрационными кнопками или имитацией покупки. \
&#x20;\
При отсутствии настроенных платежных реквизитов система должна безопасно сообщать о недоступности онлайн-оплаты. \
&#x20;\
Для технических проверок использовать изолированную тестовую среду. Реальные платежи не проводить. \
&#x20;\
Существующие ограничения доставки и региональную бизнес-логику пока не универсализировать. Если какие-либо настройки привязаны к Воронежу или особенностям старого магазина, зафиксировать их в README как обязательные пункты адаптации под клиента. \
&#x20;\
\## 8. Чего НЕ нужно делать \
&#x20;\
\- Разрабатывать CLI для создания брендов. \
\- Создавать конструктор сайтов. \
\- Реализовывать поддержку множества магазинов в одном приложении. \
\- Универсализировать оптовую логику. \
\- Переделывать складскую систему. \
\- Разрабатывать новые способы оплаты. \
\- Переписывать админку. \
\- Разрабатывать дополнительные функции. \
\- Создавать систему пресетов оформления. \
\- Создавать отдельный демонстрационный движок. \
\- Переносить реальные данные и историю миграций. \
\- Интегрироваться с LeadForge. \
\- Разрабатывать AI-инструменты. \
\- Переписывать работающую бизнес-логику. \
\- Тратить время на косметический рефакторинг. \
&#x20;\
Любое изменение должно быть обосновано необходимостью получения независимого, работоспособного магазина. \
&#x20;\
\## 9. Проверка результата \
&#x20;\
После извлечения необходимо: \
&#x20;\
1\. Убедиться, что оригинальный репозиторий не изменён. \
2\. Проверить независимый локальный запуск нового проекта. \
3\. Создать новую пустую БД и добавить демонстрационные товары. \
4\. Проверить отображение всех основных страниц. \
5\. Проверить каталог, поиск и корзину. \
6\. Проверить оформление заказа в изолированной тестовой среде. \
7\. Проверить возможность работы админки. \
8\. Проверить основные складские операции. \
9\. Проверить, что платёжная интеграция осталась технически подключаемой. \
10\. Проверить отсутствие оригинальных реквизитов в публичном интерфейсе. \
11\. Запустить TypeScript, lint и сборку. \
12\. Выполнить имеющиеся применимые тесты. \
&#x20;\
Если какую-либо функцию невозможно проверить без внешних ключей или дополнительных сервисов, не считать её проверенной. Зафиксировать это в отчёте. \
&#x20;\
\## 10. Результат \
&#x20;\
Создать независимый проект \`seedshop-template\`. \
&#x20;\
Он должен представлять собой \*\*готовый интернет-магазин с сохранённой коммерческой функциональностью\*\*, но без привязки к конкретному продавцу. \
&#x20;\
В дальнейшем процесс работы будет таким: \
&#x20;\
1\. Я нахожу потенциального клиента. \
2\. Показываю ему существующий продукт. \
3\. Предлагаю адаптацию под его магазин. \
4\. Получаю предоплату. \
5\. Через Codex адаптирую дизайн, контент, ассортимент и необходимые бизнес-настройки. \
6\. Настраиваю инфраструктуру, домен, БД, реквизиты и оплату. \
7\. Проверяю и сдаю готовый магазин клиенту. \
&#x20;\
Не нужно создавать инструменты автоматизации этих действий в рамках текущей задачи. \
&#x20;\
В конце подготовить краткий README с инструкцией запуска, основными файлами для будущего ребрендинга и перечнем обязательных клиентских настроек перед production-запуском. \
&#x20;\
\*\*Приоритет: сохранить максимум готового функционала и потратить минимум времени и токенов на извлечение независимого продукта.\*\* \
&#x20;\
Если в процессе возникнет выбор между сохранением существующего рабочего функционала и упрощением проекта, всегда отдавай приоритет сохранению функционала. Не удаляй ничего только потому, что это не требуется для первоначальной демонстрации.
