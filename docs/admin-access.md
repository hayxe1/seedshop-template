# Admin access runbook

Админка защищена внутри приложения и не зависит от функций конкретного хостинга.

Защищённые поверхности:

- `/admin/*`
- `/api/admin/*`

## Встроенная защита

- login page: `/admin/login`;
- login route: `/api/admin/login`;
- logout route: `/api/admin/logout`;
- подписанная HttpOnly cookie `admin_session`;
- middleware redirect/401;
- повторный server-side guard внутри admin pages и API.

Обязательная переменная:

```env
ADMIN_AUTH_SECRET=<independent-long-random-secret>
```

Без неё production login не должен считаться настроенным.

## Ожидаемое поведение

Без валидной сессии `/admin/*` перенаправляет на `/admin/login`, а
`/api/admin/*` возвращает `401`. После входа доступны dashboard, каталог,
остатки и заказы.

## Дополнительный периметр VPS

- Не публикуйте Next.js port `3000`; в production он привязан к `127.0.0.1`.
- Оставьте наружу только SSH, `80/tcp` и `443/tcp`.
- При наличии статического офисного IP можно дополнительно ограничить
  `/admin/*` в Caddy, но app-level login всё равно остаётся обязательным.
- Не пересылайте admin cookie и пароль в логи, скриншоты или чаты.

## Verification checklist

1. Откройте `/admin` в инкогнито — ожидается redirect на `/admin/login`.
2. Запросите `/api/admin/orders` без cookie — ожидается `401`.
3. Войдите production-пользователем и откройте dashboard, каталог и заказы.
4. Измените быстрый остаток и убедитесь, что витрина обновилась.
5. Измените статус тестового заказа и проверьте публичную защищённую ссылку.
6. Выйдите и убедитесь, что старая сессия больше не даёт доступ.

Демонстрационное заполнение не создаёт администратора. Создайте его командой `npm run admin:create` с уникальным паролем из локального окружения. Известная учётная запись существует только в отдельной E2E БД.
