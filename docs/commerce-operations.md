# Commerce operations

Этот документ описывает рабочий контур заказов после production-hardening. Источник истины по полям и связям — `prisma/schema.prisma`.

## Жизненный цикл заказа

1. Клиент отправляет `POST /api/orders` с обязательным `Idempotency-Key`.
2. Сервер повторно читает товары и наборы из PostgreSQL, фиксирует цены, изображения и состав набора в snapshots.
3. Для товаров с политикой `TRACKED` создаются резервы на 20 минут. `PREORDER` и `UNLIMITED` не блокируют складской остаток.
4. Платёж создаётся отдельной записью `PaymentAttempt` с постоянным ключом идемпотентности YooKassa.
5. Webhook не доверяет входному payload: платёж повторно читается через API YooKassa и только затем синхронизируется.
6. При первой успешной оплате резерв коммитится, остаток списывается и создаётся `InventoryMovement`.
7. Покупатель получает защищённую ссылку `/order/<token>` и может восстановить оплату без аккаунта.
8. Принятие оферты и политики фиксируется в заказе временем и версией документов.

Повторная отправка checkout с тем же ключом и теми же данными возвращает тот же заказ. Тот же ключ с другим payload возвращает конфликт, а не создаёт дубликат.

## Получение заказа

- `SELF_PICKUP` — бесплатный самовывоз. Публичный адрес не хранится и не
  показывается; менеджер сообщает место после оформления.
- `LOCAL_COURIER` — доставка только по Воронежу. Её цена не входит в платёж
  YooKassa и сохраняется менеджером после отдельного согласования.
- Legacy-значения `MANAGER_QUOTE` и `CDEK_PICKUP` остаются только для чтения
  исторических заказов.

## Операционные статусы

Разрешённый маршрут:

`NEW → PROCESSING → PACKED → SHIPPED → DELIVERED`

Из `NEW`, `PROCESSING` и `PACKED` заказ можно отменить. Отправка и завершение доступны только после успешной оплаты. Отмена оплаченного заказа помечает карточку флагом проверки оплаты: возврат денег остаётся ручной финансовой операцией.

Старое поле `Order.status` временно обновляется параллельно с `fulfillmentStatus`, чтобы откат приложения на предыдущую версию не потерял совместимость.

## Обязательные переменные окружения

```env
DATABASE_URL=postgresql://...
SITE_URL=https://example.com
NEXT_PUBLIC_SITE_URL=https://example.com
ADMIN_AUTH_SECRET=<random-32+-characters>
ORDER_ACCESS_SECRET=<different-random-32+-characters>
YOOKASSA_SHOP_ID=<shop-id>
YOOKASSA_SECRET_KEY=<secret-key>
CRON_SECRET=<random-16+-characters>
DOMAIN=example.com
```

Для уведомлений:

```env
RESEND_API_KEY=<optional>
EMAIL_FROM="Магазин семян <orders@example.com>"
TELEGRAM_BOT_TOKEN=<optional>
TELEGRAM_SELLER_CHAT_ID=<optional>
```

Уведомления полностью опциональны. Email создаётся только если одновременно заданы
`RESEND_API_KEY` и `EMAIL_FROM`; Telegram — только если заданы токен и chat id.
При пустой конфигурации владелец работает через счётчики и очередь заказов в админке.

## Webhook и фоновые задачи

- YooKassa webhook: `https://<domain>/api/yookassa/webhook`.
- Cron: `GET /api/cron/commerce` с `Authorization: Bearer <CRON_SECRET>`.
- После checkout, webhook и административных изменений доставка уведомлений запускается через `after()` — cron служит страховкой и очищает просроченные резервы/rate-limit buckets.
- В production endpoint вызывает `seedshop-template-commerce.timer` каждые пять минут.
- Перед очисткой резервов cron повторно запрашивает в YooKassa до 25 зависших платежей
  со статусом `PENDING` или `WAITING_FOR_CAPTURE`. Это резерв на случай задержки webhook
  или если покупатель не вернулся на страницу результата оплаты.
  Установка и диагностика описаны в `timeweb-vps.md`.

## Миграции и откат

Шаблон содержит новую базовую миграцию `0001_template`, построенную из текущей Prisma schema с последовательностью номеров и CHECK-ограничениями. Она предназначена для новой пустой БД, без переноса истории исходного проекта.

Перед production применением:

```bash
npm run prisma:validate
npm run prisma:generate
npm run prisma:deploy
```

При аварийном откате откатывается приложение, но не выполняется destructive down migration. Старый код продолжает работать с сохранёнными legacy-полями.

## Что мониторить

- `Order.requiresStockReview = true` — платёж пришёл после истечения резерва или остаток изменился вручную.
- `Order.requiresPaymentReview = true` — второй платёж либо отмена уже оплаченного заказа.
- `NotificationOutbox.status = FAILED` и `attempts >= 8` — нужна ручная проверка провайдера.
- `PaymentEvent.processingError` и ответы webhook 5xx — YooKassa должна повторить доставку.
- `PaymentAttempt.status = FAILED` — покупатель может повторить платёж по защищённой ссылке.

Задержанные события неуспеха прежней попытки сохраняются в её истории и не меняют актуальную попытку или её резерв. Успешная оплата любой попытки по-прежнему проверяется: второй успешный платёж требует ручной финансовой проверки.

При списании после поздней оплаты учитываются другие действующие резервы этого товара. Недостача не отбирается у другого заказа: сохраняется как количество под заказ, заказ получает флаг проверки склада. Оптовый заказ сверх остатка остаётся разрешён.

## Проверки

Перед релизом выполните `npm run check`, затем вручную проверьте checkout и повторную оплату на staging с отдельной тестовой базой и тестовым магазином YooKassa.
